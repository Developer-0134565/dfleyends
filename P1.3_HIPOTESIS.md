# P1.3 — REGISTRO DE HIPÓTESIS

> Toda hipótesis relevante se registra ANTES de intentar demostrarla.
> **No se borran las hipótesis refutadas** (§36). Una refutación es un resultado.

Estados admitidos: `CONFIRMADA` · `REFUTADA` · `PARCIAL` · `NO DEMOSTRADA` ·
`NO DISPONIBLE`

---

## H-001 — `dataset_id` (hash de contenido) identifica el estado

```
Hipótesis: El hash del contenido extraído identifica el estado del mundo.
Motivación: Es lo que el proyecto usa hoy como `state_version`.
Experimento: Comparar dos extracciones del mismo mundo a distintos tiempos.
Evidencia A FAVOR: Es determinista y reproducible: mismas entradas -> mismo hash.
Evidencia EN CONTRA:
  - P1 demostró que dos extracciones con contenido idéntico comparten dataset_id.
  - Un hash de contenido no puede distinguir dos mundos distintos con el mismo
    contenido.
  - No responde a la pregunta de freshness: cuando el mundo cambia, el hash
    cambia, pero no dice a QUÉ estado concreto corresponde el hash antiguo.
Resultado: El hash identifica el CONTENIDO, no el ESTADO. Colapsa DATASET_IDENTITY
  dentro de STATE_IDENTITY sin justificación.
Estado: REFUTADA como identidad de estado. VÁLIDA como identidad de contenido.
```

## H-002 — El tick (`frame_counter`) identifica el estado

```
Hipótesis: El número de ticks identifica unívocamente un estado.
Motivación: Es el reloj más fino expuesto por DFHack.
Experimento: Consultar la documentación de DFHack y su semántica declarada.
Evidencia EN CONTRA (literal de la documentación):
  - `Lua API.txt:2173`: `ReadCurrentTick()` "Returns the number of game ticks
    (df.global.world.frame_counter) SINCE THE START OF THE CURRENT GAME YEAR."
    → SE REINICIA cada año. No es monótono.
  - Empieza en 0 en todo mundo nuevo → dos mundos colisionan desde el tick 0.
  - Cargar un save antiguo lo hace RETROCEDER → el mismo valor designa dos
    estados distintos a lo largo del tiempo.
Resultado: El tick no es monótono, no es único entre mundos y retrocede.
Estado: REFUTADA.
```

## H-003 — `world_folder + año + tick` identifica el estado

```
Hipótesis: (world_folder, año, tick) identifica un estado.
Motivación: Es la combinación que usa la propia DFHack internamente
            (`emigration.lua`: ReadCurrentTick() + TICKS_PER_YEAR*ReadCurrentYear()).
Experimento: Ataques adversariales sistemáticos.
Ataque 1 — ¿dos mundos distintos con la misma carpeta? Sí: se puede copiar una
  carpeta de save. El componente `world_folder` no es único por diseño.
Ataque 2 — ¿(año,tick) es monótono? No: cargar un save antiguo retrocede.
Ataque 3 — ¿dos ramas desde A producen el mismo par? Sí: A→B y A→D pueden
  coincidir en año y tick, y nada en el par lo delata.
Ataque 4 — ¿el reloj avanza sin que cambie el contenido? Sí: pausa, UI y
  `script.sleep` mueven el reloj sin mutar el mundo.
Resultado: Reduce colisiones pero NO las elimina. Es un reloj, no un estado.
Estado: REFUTADA como identidad. VÁLIDA como marca temporal aproximada.
```

## H-004 — `sha256(world.sav)` identifica el save o el estado

```
Hipótesis: El sha256 del fichero de save identifica el save y su estado.
Motivación: Trivial de calcular y aparentemente sólido.
Experimento REAL (P1.3-E007): comparar la copia de respaldo con el save vivo.
Observación: SON BYTE A BYTE IDÉNTICOS. sha256 igual. Todos los campos iguales.
Resultado: Una copia del save produce el mismo hash. El hash identifica BYTES, y
  copiar es justamente la operación que preserva los bytes. No distingue el
  original de la copia, ni un estado de otro.
Estado: REFUTADA como identidad de save o de estado.
```

## H-005 — `world_folder` identifica el estado

```
Hipótesis: El nombre de la carpeta del save identifica el estado.
Experimento: ¿Cuántos estados distintos conviven en una misma carpeta?
Resultado: Todos. La carpeta contiene A, luego B, luego C; y una copia
  restaurada de A vuelve a estar en la MISMA carpeta. La carpeta es constante
  mientras el estado muta.
Estado: REFUTADA como identidad de estado. VÁLIDA como identidad de
  SAVE/MUNDO, con las reservas de E007: dos copias de la misma carpeta son
  indistinguibles.
```

```
## H-008 — `dfhack.persistent` permite un `state_id` persistente y portable

```
Hipótesis: Como `dfhack.persistent.saveWorldData` escribe en el directorio del
            save, se podría almacenar un `state_id` que sobreviva a cerrar/abrir DF
            y que viaje con la rama al cargar un save antiguo.
Motivación: Es el único mecanismo documentado de persistencia in-save (E005).
Evidencia A FAVOR (documental): la API existe y está documentada; `once-per-save`
  la usa de verdad (getWorldData/saveWorldData/deleteWorldData, líneas 25-40).
Evidencia EN CONTRA / LÍMITES:
  - Se escribe en disco SOLO AL GUARDAR el juego. Hay una ventana en la que la
    memoria y el disco divergen.
  - E009 demuestra que en estos saves NO existe tal fichero: nunca se ha usado.
  - NO se ha probado que sobreviva a "cargar un save antiguo" (PENDIENTE).
  - NO se ha probado qué pasa al duplicar un save: la copia llevaría la misma
    clave → dos saves con el MISMO state_id (ataque análogo a E007).
  - Exige que un script nuestro escriba ese dato: es una AÑADIDO, no una
    capacidad ya existente de DF.
Resultado: Es el candidato MÁS PROMETEDOR para un modelo de linaje, pero hoy es
  un ESCENARIO, no una garantía.
Estado: NO DEMOSTRADA. Requiere E7/E8 en ejecución.
```

## H-009 — `dfhack.with_suspend()` permite un snapshot atómico

```
Hipótesis: Tomando el lock de core con `with_suspend` se puede leer todo el mundo
            sin que cambie.
Motivación: La documentación dice que es "necesario para acceder a un estado
            consistente de la memoria de DF".
Experimento: Auditar documentación y el código de `exportlegends`.
Observación:
  - La documentación habla de CONSISTENCIA DE LECTURA, no de detener la simulación.
  - "Every thread is allowed only one suspend per DF frame" → el bloqueo es de
    alcance POR FRAME, no indefinido.
  - `exportlegends.lua` NO USA `with_suspend` en ningún punto (0 ocurrencias de
    `cesion_with_suspend` en el inventario automático).
Resultado: No hay evidencia de que `with_suspend` detenga el avance del mundo. Y
  aunque lo detuviera, el límite de "un suspend por frame" lo hace incompatible
  con una exportación de segundos.
Estado: NO DEMOSTRADA (el uso real observado es el contrario: no se usa).
```

## H-010 — `legends_plus.xml` es un snapshot del estado

```
Hipótesis: El fichero exportado representa una fotografía coherente del estado.
Experimento: Análisis estático del exportador (P1.3-E010).
Observación: El script cede el control (`script.sleep(1,'frames')`) al menos una
  vez POR ELEMENTO de las 22 colecciones, y entre chunks. El fichero se escribe
  incrementalmente a lo largo de esas cesiones.
Resultado: Los datos del principio se leen en un instante y los del final, en
  otro. Si el mundo avanza entre medias, el fichero MEZCLA estados.
Estado: REFUTADA. El dataset es una "eventual observation", no un snapshot.
```

## H-011 — Existe un identificador de estado interno en el binario del save

```
Hipótesis: Aunque DFHack no lo exponga, el save puede contener un UUID/ID interno.
Experimento: Analizar cabecera y cola del payload descomprimido (E007).
Observación: La cabecera es solo `version(3602)` + `flag(1)`. La cola contiene
  nombres (fortress name, world name) y etiquetas de raws. NO aparece ningún
  campo UUID ni contador global en la zona de metadata.
Resultado: No se ha encontrado. La búsqueda no es exhaustiva bit a bit.
Estado: NO DEMOSTRADA (con evidencia negativa fuerte).
```

## H-012 — Dos saves del mismo mundo en estados distintos se distinguen

```
Hipótesis: Podríamos distinguir "el estado A" de "A restaurado tras avanzar"
           comparando saves.
Experimento: Reanalizar §5 (branching).
Observación: Si A se guarda, se avanza a B, y luego se carga A de nuevo, DF
  escribe el MISMO contenido de estado en el mismo directorio. Nada en DFHack
  registra que existió una B.
Resultado: Solo un mecanismo EXTERNO al estado del juego (un registro de linaje)
  puede distinguir "A nunca avanzó" de "A se restauró tras avanzar".
Estado: REFUTADA dentro del estado del juego; PARCIAL para un linaje externo
  (ver H-008).
```

## H-013 — `region1` y `region2` son un único estado coherente

```
Hipótesis: Los ficheros del directorio de save representan un único estado.
Experimento: Analizar ambos contenedores (P1.3-E008).
Observación: region1/world.sav = 208 MB descomprimidos; region2/world.dat =
  78 MB. Hashes y tamaños distintos. Se escriben en momentos distintos
  (17:26:56 vs 17:36:59).
Resultado: Son dos sub-estados con ciclo de vida independiente. Un "estado del
  mundo" definido sobre uno de ellos será necesariamente incompleto respecto
  del otro.
Estado: REFUTADA.
```

## H-014 — Se puede demostrar que una evidencia ha quedado obsoleta

```
Hipótesis: El sistema puede saber que una evidencia que era verdadera dejó de
            representar el estado actual.
Observación de partida: hoy no existe ningún reloj de mundo persistido en el
            dataset; `dataset_id` solo cambia cuando cambia el contenido.
Experimento: ¿Qué información mínima haría falta?
  - Un identificador del mundo (H-005, válido).
  - Una marca del estado en el momento de observar (H-003, reloj aproximado).
  - Un contador persistente de guardado/linaje (H-008, no demostrado).
Resultado: Sin al menos dos de esos tres, NO se puede distinguir
  "sigue siendo verdad" de "ya no lo es". Con el estado actual del proyecto,
  la freshness es INDETERMINABLE.
Estado: NO DEMOSTRADA. Es el bloqueo central de §27.
```

Resultado: El mtime depende de CUÁNDO se copió, no de QUÉ contiene.
  `cp -p` lo conserva y sigue siendo una copia; `touch` lo falsifica sin
  cambiar un byte del contenido.
Estado: REFUTADA.
```
